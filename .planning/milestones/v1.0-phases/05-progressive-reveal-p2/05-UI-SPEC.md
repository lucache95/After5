The reveal ladder lives across all three brand tiers. The contract honors the existing three-tier split rather than a single 60/30/10 page, because the blurred host hint sits on Tier-2 experience surfaces (the photo leads) and the full reveal sits on a Tier-3 neutral profile surface (humans read un-branded).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `shell.base` `#FAF4EC` (Tier-1/2 chrome) · `profile.base` `#FAFAF8` (Tier-3 reveal sheet) | App shell + ceremony sheet background |
| Secondary (30%) | the date's `vibePalette` `bg` (Tier-2 card chrome) · `profile.tag` `#E5E5E0` (Tier-3 chips) | Card/detail chrome around the photo; neutral profile chips |
| Accent (10%) | `shell.accent` `#E0218A` (hot pink) | See reserved list below |
| Success | `sage` `#5CDBA0` | The ceremony "locked in / revealed" confirmation beat ONLY (see §5b promotion note) |
| Destructive | not used this phase | No destructive actions in the reveal flow |

Accent reserved for:
- the primary ceremony CTA ("slide in") on the post-reveal sheet,
- the soft Barbiecore flourish on the ceremony (a single hot-pink sticker/glow accent — one element, not a wash),

## Reveal-Ladder Visual Contract (phase-specific, normative)

This is the load-bearing section. Three rungs, blur-driven. Name + age are known from the feed onward (D-01); only the FACE un-blurs heavy → light → clear.

| Rung | Surface(s) | Host avatar | Name + age | Other identity |
|------|-----------|-------------|------------|----------------|
| 1 — Pre-match | feed `NightCard`, `NightDetailSheet`/`NightDetailNight` | heavy blur (see strengths) | shown, Label 14px lowercase | none (no neighborhood/venue/photos/handle) |
| 2 — Offer | `InterestedList`, offer / `MakeOfferModal` flow | light blur (one step softer) | shown | none beyond rung 1; the NIGHT still leads — face is secondary |
| 3 — Threshold (post-lock) | `RevealModal` + `LockDetail` + `MatchConfirmation` | clear, animated un-blur ceremony | full name + age | full Tier-3 `ProfileCard` (photos, prompts, vibe chips); contact (instagram) only if caller passes it |

### Blur strengths (Claude's Discretion — DECIDED)

Decision: **CSS `blur()` on a single signed source asset, not a second pre-generated blur tier.**

Rationale: `generate-blur` produces exactly one `blurred_photo_url`/`blurred_path` (denormalized mirror of the primary photo — confirmed in `apps/web/lib/after5/photos.ts`). Generating a *second* blur level means a new edge-fn output column, a backfill, and more prod-apply surface — disproportionate for one rung of softening. Applying an additional CSS `blur()` over the already-blurred signed asset is cheap, reversible, and keeps the pipeline untouched. The pre-generated blur is the privacy floor (the raw face never reaches the client pre-lock); CSS only ever *adds* blur on top of it, never removes — so it cannot leak the clear face.

Per-rung strength (CSS `filter: blur()` applied to the signed `blurred_photo_url`):

| Rung | Effective blur | Implementation |
|------|----------------|----------------|
| 1 — Pre-match (heavy) | strong | render `blurred_photo_url` + add CSS `blur(8px)` on top → heavy, face unreadable |
| 2 — Offer (light) | softened one step | same `blurred_photo_url` + CSS `blur(3px)` → face starts resolving, still not identifiable |
| 3 — Threshold (clear) | none | swap to the reveal-gated signed CLEAR url (`signClearUrls`); zero CSS blur |

Privacy invariant: rungs 1 and 2 NEVER fetch the clear path. The client only ever holds `blurred_photo_url` pre-lock; the clear url is signed only when `match_reveal_allowed`/`match_reveal_allowed_pair` passes (post-lock). CSS blur is presentation-only over an already-safe asset.

`signBlurredUrls()` scope (Claude's Discretion — DECIDED): mirror `signClearUrls()` in `apps/web/lib/after5/photos.ts` but sign the `blurred_path` with a permissive scope — blurred photos are pre-match-safe (they are the privacy artifact), so they may be signed for any authenticated viewer who can see the night, without the reveal gate. Same `createSignedUrls` mechanism, longer-lived TTL acceptable (e.g. 600s, matching clear). Confirm the storage RLS allows authenticated reads of `blurred_path` before relying on it; if not, the planner adds a permissive read policy for blurred objects only (never clear). Do NOT loosen the clear-path policy.

`FeedNight` host-hint extension (Claude's Discretion — DECIDED): extend `FeedNight` (in `packages/api-client/src/feed.ts`) with exactly three new fields and nothing more, preserving the blind contract (no `creator_id`, no `itinerary_id`, no precise venue/location beyond the existing `venue_neighborhood`):

```ts
host_blurred_photo_url: string | null;  // signed blurred-photo url (NOT clear)
host_first_name: string | null;         // first name only — never full name
host_age: number | null;                // age only — never DOB
```

These come from the existing pre-offer host-disclosure scope (`20260527127400_p5_host_pre_offer_disclosure.sql`). If `browse_feed_for_viewer` cannot project them blind-safely, project via a separate limited host-hint read rather than widening the feed RPC's identity surface.

### Identity-led, not photo-led (rungs 1 + 2)

- `NightCard`: cover photo (the experience) remains the hero. The blurred host avatar is a small 48px circular thumbnail in the card footer/meta row with the name+age label beside it — secondary, never the visual focus. Polaroid framing is for the EXPERIENCE photo, not the blurred host avatar (DESIGN-SYSTEM §5).
- `InterestedList` / offer flow: the night's plan + expectations lead. The light-blur host avatar is a supporting detail, same 48px footprint, not a full-bleed photo. "experience-led (not photo-led)" is a hard acceptance criterion (REQ-E15) — the checker/auditor will reject a clear-photo-forward offer surface.

## The Ceremony (D-04, REQ-E16) — Interaction Contract

Surface: enhance the existing `RevealModal.tsx` (a `vaul` bottom sheet on `profile.base`). Crossing the post-lock threshold renders a deliberate, earned reveal — animated un-blur dissolve + a single subtle Barbiecore flourish + a `sonner` toast. Earned and warm, never confetti-loud (no match-confetti burst here — that lives on the match screen; the reveal is quieter and more intimate).

Animation mechanics (Claude's Discretion — DECIDED, framer-motion per DESIGN-SYSTEM §6):

1. Sheet opens (vaul spring). The host photo mounts at the rung-2 light-blur state (CSS `blur(3px)`), so the moment reads as continuous with the offer stage.
2. **Un-blur dissolve:** animate CSS `filter` from `blur(12px)` (a beat heavier than rung-1, for drama) → `blur(0px)` over ~900ms with `ease: [0.22, 1, 0.36, 1]` (a soft expo-out), paired with a subtle `scale` 1.02 → 1.0 and `opacity` 0.85 → 1. The face resolves into focus. Source asset is the now-signed CLEAR photo (gated by `match_reveal_allowed`).
3. **Flourish:** one hot-pink sticker/soft-glow element (a single sparkle or soft radial glow behind the polaroid, `shell.accent`, deterministic tiny rotation per §5b) fades in at ~600ms with a gentle scale, then settles. One element. No bursts.
4. **Toast:** fire a `sonner` toast at reveal completion with the reveal copy (see Copywriting). Toast, not a modal-on-modal.
5. Settle into the full Tier-3 `ProfileCard` (name+age heading, prompts, vibe chips) already rendered by `RevealModal`.

Timing budget: total choreography ≤ ~1.4s, front-loaded on the un-blur. The reveal should feel like a breath, not a loading bar.

Reduced-motion fallback (Claude's Discretion — DECIDED, REQUIRED): respect `prefers-reduced-motion: reduce` (use framer-motion `useReducedMotion()`). When reduced: NO blur-to-clear animation, NO scale/glow motion — render the clear photo immediately at full clarity with a single ≤200ms opacity cross-fade, still fire the `sonner` toast, still show the flourish element statically (no entrance motion). The emotional beat (the toast + seeing the face) survives; only the motion is removed. Accessibility is taste (DESIGN-SYSTEM §9).

`identity_revealed` dispatch (Claude's Discretion — RESEARCHER NOTE for planner): the `identity_revealed` notification type is already applied (D11). The planner MUST confirm against the lock/accept RPC path whether the dispatch site exists. Per CONTEXT D-02 the threshold = the moment both sides lock (accept). Expected dispatch site: the accept/lock DEFINER RPC that flips the pair to locked — dispatch `identity_revealed` to BOTH parties there (mirror the E8 `interest_received` dispatch pattern from `match_ingest_interest`), deep-linked to `/matches/[lockId]`. If no dispatch site exists, this is wiring (a `dispatch_notification` call inside the existing RPC), not a migration.

States (DESIGN-SYSTEM §7 — every screen): the ceremony sheet must handle loading (clear photo signing in flight → show the light-blur held state, never a spinner-on-empty), the no-photo fallback (reuse `ProfileCard`'s Polaroid gradient fallback — no broken-image), and error (signing fails → keep the light-blur, show a quiet "couldn't load the photo, pull to retry" line; the match + plan are still reachable). Skeletons over spinners.

## Copywriting Contract

Tone: lowercase, dry, Barbiecore, stop-slop. No em-dashes, no filler, no adverbs, no "Welcome/Continue/amazing". Reuse the canonical match copy ("you cooked." / "slide in") so the reveal feels of-a-piece with the existing match screen.

| Element | Copy |
|---------|------|
| Primary CTA | `slide in` (post-reveal sheet → opens chat with the now-revealed match) |
| Rung-1 host hint label | `{first_name}, {age}` (lowercase, e.g. `maya, 27`) — no tagline, no "host" word; the blurred face says the rest |
| Rung-2 (offer) host hint | same `{first_name}, {age}` label; no new copy — the only delta is the softer blur |
| Reveal headline (ceremony) | `you cooked.` (Display) — the canonical match line, reused at the reveal beat |
| Reveal sub-line | `here's {first_name}.` (lowercase, one line, sets up the face) |
| `identity_revealed` toast (sonner) | `the face behind the night. say hi.` |
| Empty state — no host photo at reveal | heading `camera shy.` · body `{first_name} skipped the photo. you'll see them on the date.` (Polaroid fallback renders) |
| Error state — clear photo fails to load | `couldn't load the photo. pull to retry. the plan's still locked in.` |
| Loading (signing in flight) | no copy — hold the light-blur state, no spinner |

Destructive actions: none in this phase. The reveal is additive and irreversible-by-design (you've already both locked); there is no "un-reveal" control, so no destructive confirmation.

Stop-slop note for the executor: the existing `PostNightForm.tsx:315` em-dash is a known LOW finding (STATE.md) — do not introduce new em-dashes in any reveal copy. Lowercase all headlines + CTAs.
