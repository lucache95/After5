# Phase 6 — UI Design Contract

> Visual and interaction contract for Trust & Safety (P2). Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> Surfaces: reliability badge on the revealed ProfileCard (E17); the 4 chat↔profile↔night nav edges (E18); the "still on?" reconfirm + "all good?" safety check-in surfaces (E19). This phase WIRES existing infra — it does not introduce a new design system. All dating-vertical Barbiecore per `docs/superpowers/DESIGN-SYSTEM.md`.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gap inside the reliability pill, chip inner gap |
| sm | 8px | Compact gap (badge row, nav-edge icon gaps) — Tailwind `gap-2` |
| md | 16px | Default surface padding — `p-4` reconfirm/check-in cards |
| lg | 24px | Section padding inside ProfileCard / LockDetail blocks — `p-5`/`space-y-5` |
| xl | 32px | Layout gaps between LockDetail sections |
| 2xl | 48px | Major section breaks |
| 3xl | 64px | Page-level spacing (rare on these phone surfaces) |

Exceptions:
- **Tap targets ≥44px** (`h-11 w-11`) for the new icon-only nav controls (back-chrome, the profile/night quick-links) and the check-in action buttons. This is a DESIGN-SYSTEM §4 / §9 rule, not a spacing violation — it is the existing `DeepRouteHeader` control size.
- ProfileCard already uses `p-5` (20px) and `space-y-5` for its internal rhythm; the reliability row inherits that, it does not introduce a new value.

## Typography

Dating surfaces (shell + profile). Two weights only: regular (400) and semibold (600). 4 roles.

| Role | Size | Weight | Line Height | Notes |
|------|------|--------|-------------|-------|
| Display | 30px (`text-3xl`) | 400 | 1.05–1.1 | ProfileCard name heading (`font-heading` lowercase). Unchanged by this phase. |
| Heading | 20px (`text-xl`) | 400 | 1.2 (`leading-tight`) | DeepRouteHeader title (counterpart name in chat); reconfirm/check-in card title ("still on?", "all good?") in `font-heading` lowercase. |
| Body | 16px (`text-[16px]`) | 400 | 1.5 (`leading-relaxed`) | Card body copy, check-in question line, soft-warning explainer (`font-body`). |
| Label | 13px (`text-[13px]`) | 600 | 1.3 | Reliability pill text, vibe chips, the small uppercase prompt labels, nav-edge link labels. The "new member" treatment uses this size. |

Reliability score number, when shown, renders at Body size (16px, weight 600) inside the pill — it is a label-with-emphasis, not a display number. Do NOT render the score as a large hero figure (it would read as a credit score / punitive — violates D-01 "encouraging, not punitive").

## Color

Three-tier system from DESIGN-SYSTEM §1. This phase touches two tiers: **Tier 1 shell** (LockDetail reconfirm/check-in surfaces, chat header) and **Tier 3 profile** (the reliability badge lives on the neutral ProfileCard).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `shell.base` `#FAF4EC` (shell surfaces) / `profile.base` `#FAFAF8` (ProfileCard) | Page + card backgrounds |
| Secondary (30%) | `shell.ink/[0.04–0.06]` washes, `profile.ink/[0.04–0.06]` | Reliability pill background, reconfirm/check-in card fill, prompt cards |
| Accent (10%) | `shell.accent` `#E0218A` | See reserved-for list below |
| Success (semantic) | `sage` `#5CDBA0` | "established / reliable" affirmation tick on the reliability pill ONLY (promote to a token when used — currently reserved, not in `tailwind.config.ts`). Never as a general accent. |
| Soft wash (semantic) | `blush` `#FFB3D1` | The "new member" reliability treatment background + the soft-warning ("no reply yet") wash — warmer than `shell.pink`, reads encouraging not alarming. Promote to token on use. |

Accent (`shell.accent`) reserved for, this phase:
- The chat-header quick-link to the **night/plan** if rendered as a primary pink chip (otherwise it is a quiet ink link — see Components).
- Active/focus ring on all new interactive controls (`ring-shell-accent/40`) — existing pattern.
- The "something's wrong" path's confirm action label (the path itself is quiet; only its commit affordance carries accent).

Explicitly NOT accent-colored (avoids accent dilution + avoids alarm):
- The reliability "new member" treatment → `blush` soft wash, never pink-flood, never red.
- The reconfirm "still on?" and check-in "all good?" cards → neutral `shell.ink/[0.05]` fill; warm, not pink-loud, never red/destructive coloring (D-03/D-04: soft, notify-only, not alarmist).
- The soft-warning "no reply yet" state → `blush`/amber-warm wash at low opacity, NOT `shell.accent` and NOT a destructive red. A missed reconfirm is a nudge, not an error.

No destructive (red) color is introduced in this phase. The only existing destructive-adjacent action ("cancel this date") already lives in LockDetail with a neutral outlined-ink treatment and a `vaul` reason-picker — this phase does not add a red. "something's wrong" routes to mod/admin silently (fail-loud server-side per `dispatch_notification`), and stays a quiet text affordance in the UI, not a red alarm button.

## Copywriting Contract

All copy: lowercase, dry, Barbiecore, stop-slop — no em-dashes, no filler, no motivational/startup voice, warm not alarmist (DESIGN-SYSTEM §3, project stop-slop rule).

| Element | Copy |
|---------|------|
| Primary CTA (reconfirm) | `still on?` — two soft replies: `yep, still on` / `gotta bail` (the bail path surfaces the existing cancel flow; it does NOT auto-cancel, D-04) |
| Primary CTA (safety check-in) | `all good?` — primary `all good` ack; quiet secondary text-link `something's wrong` |
| Reliability — established | a small `sage` tick + label `reliable` next to the score pill (e.g. `94% · reliable`). Range 0–100 (see Discretion). |
| Reliability — new member | `new here` (blush pill, no number). Subtext on the profile if space: `no rated dates yet`. Encouraging, never `unrated`/`unreliable`/`unproven`. |
| Empty state heading (no reliability data, established-but-zero edge) | `new here` (falls back to the new-member treatment — there is no separate empty state; absence of ratings IS the new-member state, badgeFor isNew=true) |
| Empty state body | `no rated dates yet. it builds after a few nights.` |
| Error state (reconfirm/check-in dispatch failed, client view) | the surfaces are notify-driven and read-mostly; if an in-app ack POST fails, toast (`sonner`): `didn't go through. try that again.` |
| Soft-warning (reconfirm, no reply) | shown to both parties as a quiet line on LockDetail: `no reply on the day-of check yet.` No CTA escalation, no red. |
| Check-in acknowledged confirmation | toast: `good. have fun.` |
| "something's wrong" confirmation | toast after dispatch: `flagged. someone's on it.` (the alert routes to mod/admin via the existing safety chain) |
| Nav-edge labels (E18) | chat header → profile: `their profile`; chat header → night: `the night`; profile → night: `see the night`; night → profile: `their profile` (reuses LockDetail's existing `see their profile`); night → chat: existing `message {name}` (unchanged) |
| Destructive confirmation | none introduced this phase. The existing `cancel this date` flow (neutral outline + `CancelWithReasonPicker` in a `vaul` drawer) is unchanged. The reconfirm "gotta bail" path REUSES that same flow — it is not a new destructive surface. |

## Component Inventory & Surface Map

Prescriptive placement so the executor has no design ambiguity. All reuse existing components; nothing net-new in dependency terms.

### E17 — Reliability badge (Tier 3, on `ProfileCard.tsx`)
- **Where:** inside the `<header>` block of `ProfileCard`, directly under the name heading (line ~70–75), as a pill in the meta row. Driven by `badgeFor({ verification, reliability_score })` from `@after5/business` + the `public_profile_card` view's `reliability_score` / `badge_is_new`.
- **Visual:** a single rounded-full pill, `text-[13px]` semibold, Tier-3 neutral.
  - `isNew === true` → `new here` on a `blush`-tint pill (`bg-[#FFB3D1]/25 text-profile-ink/80`). No number. Optional subtext line below at `text-[13px] text-profile-ink/50`: `no rated dates yet`.
  - `isNew === false` → `{score}% · reliable` with a small `sage` tick (`lucide-react` `Check` or a 6px dot), `bg-profile-ink/[0.06]`. The `sage` tick is the ONLY non-neutral color on this Tier-3 surface, kept tiny.
- **A11y:** the pill carries an `aria-label` spelling it out (`reliability: 94 percent, established` / `new member, no rated dates yet`). Verified badge (existing `badge_verified`) sits beside it, unchanged.
- **Score range:** 0–100 integer percent (Claude's Discretion — see rationale). New-member shows no number at all.

### E18 — The 4 nav edges (reuse `DeepRouteHeader` + reveal-gated surfaces)
Post-lock identity is already revealed (Phase 5), so the chat header may link to the revealed profile and the night.

1. **Chat → Profile + Chat → Night** (`messages/[threadId]/page.tsx`): pass the existing `DeepRouteHeader` `right` slot two compact controls — a profile quick-link and a night quick-link. Each is a ≥44px tap target.
   - Profile link → `/matches/[lockId]` reveal surface (or a `?profile` deep-link to the ProfileCard), label `their profile`.
   - Night link → `/matches/[lockId]` (the night/plan), label `the night`.
   - These require the thread's `lock_id` (chat_threads carries `offer_id`/`lock_id`); the loader must select it. If the thread is not yet lock-promoted (pre-lock), render NO profile/night control (reveal-gated — do not leak identity pre-lock).
   - Render as quiet ink links/icon-buttons in the header `right` slot. Pink reserved for at most one (the night) if a primary affordance is wanted; default both quiet.
2. **Profile → Night** (`ProfileCard`/reveal surface or LockDetail): a `see the night` text-link/button. On LockDetail the night already renders in-page (the PlanTimeline section), so "Profile → Night" within LockDetail is a scroll-to / existing section; from a standalone profile route it is a `Link` to `/matches/[lockId]`.
3. **Night → Profile** (`LockDetail.tsx`): the existing `see their profile` button (line ~98–104) IS this edge — unchanged, confirmed satisfying the contract.
4. **Night → Chat** (`LockDetail.tsx`): the existing `message {name}` link (line ~115–121) — unchanged (already the one working edge).

### E19 — Reconfirm + check-in surfaces (Tier 1 shell, on `LockDetail.tsx` / matches surfaces)
These are notify-driven (jobs dispatch `date_reconfirm` / `safety_checkin` notifications). The in-app surfaces are light states rendered on the existing LockDetail page, gated by lock/job state passed from the loader. Keep them small — a card, not a takeover.

- **`still on?` reconfirm card** (renders on LockDetail morning-of, when a `day_of_reconfirm` is live and unacked):
  - A `rounded-3xl bg-shell-ink/[0.05] p-4` card above the night section. Title `still on?` (`font-heading text-xl lowercase`). Two buttons: `yep, still on` (semibold ink on a soft fill) and `gotta bail` (quiet outline → opens the existing cancel flow). No red.
- **Soft-warning state** (no reply by the window): a single quiet line on both parties' LockDetail — `no reply on the day-of check yet.` on a `blush`/amber low-opacity wash. No CTA, no escalation, no red (D-04).
- **`all good?` safety check-in card** (renders post-date-window when a `safety_checkin` is live and unacked):
  - Same card chrome. Title `all good?`. Primary `all good` ack button. Quiet secondary text-link `something's wrong` → on tap, a `vaul` confirm sheet `flag this date?` with a single `yes, flag it` (the only accent-carrying affordance here) that dispatches `safety_alert`. Acks/flags fire `sonner` toasts per the copy contract.
- **Render location decision (Discretion):** all three live in `LockDetail.tsx` as conditional blocks driven by loader-provided flags (`reconfirmDue`/`reconfirmNoReply`/`checkinDue`), mirroring how `ratingOpen` already gates the "rate this date" block. This keeps the date's whole lifecycle on one surface and avoids a new route.

## Motion & States (DESIGN-SYSTEM §6/§7)

- Every new surface declares loading / empty / error / success. The reliability pill has no async of its own (server-provided). The check-in/reconfirm acks are optimistic with a `sonner` toast on success and a retry toast on failure.
- Card entrances: gentle `framer-motion` fade/slide-up (reuse the LockDetail section rhythm), spring physics, `motion-reduce` honored.
- No confetti / no alarm animation on safety surfaces — warmth, not drama (D-03 "soft", §Specifics "warm, not alarmist").
- Focus-visible ring `ring-4 ring-shell-accent/40` on all new controls (existing pattern).

## Claude's Discretion — decisions recorded (per 06-CONTEXT.md Claude's Discretion + autonomous mode)

1. **Reliability score range = 0–100 integer percent.** Rationale: D-01 calls it a "weighted percentage"; a percent reads natively as "% positive outcomes" and the badge already has room for `94% · reliable`. 0–5 stars would imply a per-date rating average (it isn't — it's an aggregate) and invites a punitive star-rating mental model. Percent + a `reliable` word-label keeps it warm and legible.
2. **New-member visual = `blush` pill, word-only (`new here`), no number, no red, no pink-flood.** Rationale: D-01 + §Specifics — a new member is unrated, not unreliable. `blush` (#FFB3D1) is the documented soft-encouraging wash; `sage` tick is reserved strictly for the established/affirmation case so it doesn't dilute.
3. **`sage` is the only non-neutral accent allowed on the Tier-3 ProfileCard, and only as a tiny tick.** Rationale: Tier-3 is meant to strip branding (§1); a single success-tick is the minimum signal for "established" without re-branding a neutral surface.
4. **Reconfirm + check-in render inline on `LockDetail.tsx`** (not a new route, not a modal takeover), gated by loader flags mirroring the existing `ratingOpen` pattern. Rationale: CONTEXT Discretion says "reuse LockDetail / matches surfaces; keep them light"; one surface owns the date lifecycle.
5. **Chat→profile/night controls live in `DeepRouteHeader`'s `right` slot**, quiet by default, reveal-gated on `lock_id` presence. Rationale: DeepRouteHeader already exposes a `right` slot and a `title`; using it keeps the four edges consistent with E1 nav chrome and avoids leaking identity pre-lock.
6. **No new red/destructive token.** Rationale: D-02/D-03/D-04 are all soft/notify-only; the only "bail"/"flag" affordances reuse the existing cancel flow or a single accent confirm. Introducing red would read as enforcement, which is explicitly deferred.
