<objective>
Make dating preferences editable post-signup (REQ-E4 / D-09): extract the existing `PreferencesStep` form body into a shared, mode-aware `<PreferencesForm>` (onboarding advances the step machine; account saves + toasts + stays), build a new auth-gated `/account/preferences` route that hydrates the current prefs, and relocate the dating on/off toggle here from `EnableDatingButton`.

This is an independently-shippable vertical slice: after it lands, a real logged-in user can change who they see (age/distance/gender/dealbreakers) and pause/resume dating from a real settings page — capabilities that today are write-once at `/onboarding/preferences` with no link back.

**LOCKED dating-OFF semantics (A3):** turning dating OFF = stop NEW exposure only — set `dating_enabled=false` (excluded from feed eligibility, blocks NEW incoming interest). It MUST NOT auto-cancel or withdraw existing active offers/locks (those are commitments that resolve naturally). Implement least-destructive; flag in a code comment as a founder-overridable assumption.

Purpose: One obvious "settings" destination, cleanly separated from identity display; the prefs the S5 feed pre-filter reads become user-editable.
Output: extracted `parseAgePref` util + `StickerChip` + `PreferencesForm`, refactored onboarding step (behavior-preserving), new `/account/preferences` page, and unit + E2E tests.
</objective>

| T-03-02 | Elevation of Privilege | client-supplied userId on the prefs/dating write | mitigate | V4: derive `userId` server-side from the session and pass to the form; `savePreferences`/toggle write `.eq('id', userId)` and RLS `auth.uid()` is the backstop — a forged id cannot write another user's row. |
| T-03-03 | Input Validation | prefs payload | mitigate | V5: validate via existing `PreferencesInputSchema` (zod) before `savePreferences`; reuse, do not bypass. |

| T-03-05 | Tampering | dating age-gate bypass | mitigate | The dating toggle reuses the existing gated write; the DB age-gate trigger stays the hard enforcement — the form must not bypass it. |
| T-03-SC | Tampering | npm/pip/cargo installs | accept | Zero new packages (RESEARCH Package Legitimacy Audit "Not applicable"); `sonner`/`vaul`/`zod` already in production. |
