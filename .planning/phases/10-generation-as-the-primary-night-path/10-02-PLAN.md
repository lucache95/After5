<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser→POST /api/profile/city | Untrusted {cityId} crosses here; writes the user's home-city (location-adjacent profile data) |
| route→profiles | Self-scoped write under RLS (auth.uid()) |
| route→job queue | enqueue runs in admin context (enqueue_job is REVOKED from authenticated) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-03 | Spoofing | POST /api/profile/city | mitigate | createClient().auth.getUser() → 401 on anon; write is .eq('id', user.id) under profiles_owner_all RLS, so a user can only set their own primary_city_id. |
| T-10-04 | Tampering | cityId input | mitigate | zod uuid validation + existence check against cities where is_active before the write — a hostile/unknown id returns 400, never reaches the FK write. |
| T-10-05 | Information Disclosure | home-city PII | accept | primary_city_id is coarse city-level (not precise location); only self-readable/writable; surfaced only to the owner and to feed-centroid scoping that already exists (E10/E23). |
| T-10-06 | Elevation of Privilege | enqueue from request | mitigate | enqueue stays in the admin-context helper (enqueueSeedCity), invoked server-side only; never exposed to the browser; cityId re-validated as uuid inside the helper. |
| T-10-07 | Denial of Service | repeated city sets / many users same city | accept | enqueue dedups per city (p_dedup_key = cityId) → at most one pending seed per city; handler backoff dead-letters at attempts>=5. |
</threat_model>
