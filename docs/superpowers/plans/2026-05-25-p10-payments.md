# P10 — Payments Decision (Pay-Setting Integrity) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the payments integrity gap left by the spec's "who pays" setting. The setting (`itineraries.pay_setting`, enum `i_pay`/`they_pay`/`split`, landed in P0) is *implied* to be a solved promise but moves no money and creates no obligation — a person can publish "I pay," lock a night, and then not pay. This phase makes a **decision** about that gap, then implements the chosen path end-to-end with tests.

**The decision (read first):** see **§ DECISION GATE** below. We **recommend and implement Option (b): relabel `pay_setting` as a non-binding social *convention*, not a transaction.** We surface an explicit disclaimer everywhere the setting renders, and we extend the P0 `reports` intake with a **`payment_dispute` category** so abuse/expectation problems are *trackable and moderatable* even though no money flows. **Option (a) — Stripe Connect holds/escrow — is documented as a clearly-marked FUTURE design section with no TDD tasks** (it is post-launch, premium-gated, and carries regulatory weight we explicitly defer).

**Architecture:** Build on P0. No money movement, no payment processor, no new financial PII. The work is: (1) a single source-of-truth **copy/disclosure module** in the shared `@after5/business` package (pure functions, no I/O — reused by web today and native later, per spec §10), (2) a Zod **report-reason** schema in `@after5/validators` that adds the `payment_dispute` category, (3) one small SQL migration extending the P0 `reports` table with a typed `reason_category` enum + a CHECK that payment disputes carry a `pay_setting` snapshot, and (4) web UI that renders `pay_setting` with the non-binding disclaimer wherever the night's pay setting is shown (browse feed card, offer/reveal detail). Invariants that *can* live in the DB (the report category is closed-set; a payment dispute must reference a date) live in the DB.

**Tech Stack:** Supabase Postgres + SQL migrations (`supabase/migrations/`), RLS reused from P0, psql invariant tests in `supabase/tests/`; shared TS in `packages/business` + `packages/validators` tested with **vitest** (introduced here — the repo has no test runner yet); Next.js 15 / React 19 web UI in `apps/web` (Tailwind + the existing `cn()` util), component-level vitest + Testing Library for the disclaimer render assertion.

**Source docs:** spec `docs/superpowers/specs/2026-05-25-experience-first-dating-core-loop-design.md` (§4 "Pay setting" — *"An expectation, not a binding transaction; renegotiable/cancellable post-lock without penalty… Payment-related reports are tracked."*); roadmap `docs/superpowers/plans/2026-05-25-experience-first-dating-implementation-roadmap.md` (Phase 10, "Closes: Critical #5 payments integrity gap, pay-setting abuse/expectation problems"); foundation `docs/superpowers/plans/2026-05-25-p0-data-model.md` (the `pay_setting` enum on `itineraries`, the `reports` table, the `browse_feed` view).

**Reconciliation note (vs P0):** P0 created `payment_preference` enum (`i_pay`/`they_pay`/`split`), `itineraries.pay_setting payment_preference`, the `reports` table (with free-text `reason` + a `target_type` CHECK and `status` CHECK), and the `browse_feed` view that already projects `i.pay_setting`. P10 **extends** `reports` (adds `reason_category` + a payment-dispute constraint) and **consumes** `pay_setting` in the UI/copy layer. P10 introduces **no new enums on `itineraries`** and does not alter `payment_preference`. The spec's exact human-facing strings ("I pay" / "they pay" / "50-50") are *display* mappings of the enum and live in the copy module, never duplicated in the DB.

**Conventions (follow exactly):** migration filenames `YYYYMMDDHHMMSS_snake_description.sql` (P10 block uses the `202605251213NN` series, after P0's `202605251211xx`); enable RLS on every new table (none added here — we extend `reports`); create/alter policies idempotently with `DO $$ BEGIN … EXCEPTION WHEN duplicate_object THEN NULL; END $$;`; `auth.uid()` in policies; pure shared logic goes in `@after5/business` (no I/O) and schemas in `@after5/validators` (Zod) — both already workspace packages; web components live in `apps/web/components`, use `cn()` from `apps/web/lib/cn.ts`.

## DECISION GATE — Binding payment vs. social convention

**The gap.** Spec §4 lists `pay_setting` as one of `I pay` / `they pay` / `50-50` and *already says* it is "an expectation, not a binding transaction; renegotiable/cancellable post-lock without penalty." But the product surfaces it like a feature, and the audit flags it (Critical #5) because nothing in the system makes it *true*: there is no hold, no escrow, no charge, no proof, and no recourse when someone publishes "I pay" to attract responders and then doesn't. That is the **payments integrity gap** and the **pay-setting abuse/expectation problem** this phase must close.

Two paths close it:

### Option (a) — Make it binding (Stripe holds / escrow)
Put real money behind the setting: when a night locks, place an authorization hold / escrow for the paying party, capture or release at completion, refund on benign cancellation, arbitrate on dispute.

- **Pros:** the promise is real; reduces a class of bad-faith behavior; enables a future premium/marketplace business.
- **Cons (why not for launch):**
  - **Regulatory + compliance weight.** Holding/transmitting funds pulls in money-transmission/marketplace rules, KYC on payees, Stripe Connect onboarding, tax/1099-style reporting, chargeback handling, and refund/dispute SLAs. That is a whole compliance surface, not a feature.
  - **New high-risk PII** (payment instruments, payee identity/bank data) — exactly what we avoided collecting in P0.
  - **Marketplace cold-start tax.** In a thin single-city launch (spec §9), forcing payment friction onto the *very first* dates suppresses the liquidity we're trying to ignite.
  - **It contradicts the spec.** §4 explicitly designs the setting as *renegotiable/cancellable without penalty* — escrow with auto-capture fights that intent. Escrow only makes sense once a paid/premium tier justifies it.
  - **Cost & build time** dwarf the actual launch need (the launch need is "stop implying a guarantee we can't keep").

### Option (b) — Relabel as a non-binding social convention  ✅ RECOMMENDED & IMPLEMENTED
Treat `pay_setting` as **a heads-up about the vibe**, never a transaction. Concretely:
1. **UI copy** everywhere the setting renders carries a short, explicit **non-binding disclaimer** ("a heads-up, not a guarantee — sort it out in person"). Source-of-truth strings live in one shared module so web + native + any future surface stay consistent.
2. A **`pay_setting` disclosure** appears at the point a night is published *and* at the point a responder sees it (browse + offer reveal), so neither side can claim they were promised a payment.
3. The P0 **`reports`** intake gains a **`payment_dispute` category** so when the convention is abused ("they said they'd pay and bailed on the bill"), it is *captured, categorized, and routed to moderation* (P8) and feeds the reliability/enforcement ladder (P7) — without the platform ever touching money.

- **Pros:** cheap, ships now, **removes the integrity gap immediately** (we stop implying a guarantee), no regulatory exposure, no new financial PII, faithful to spec §4, and still gives T&S a lever (tracked disputes).
- **Cons:** does not *enforce* payment. Accepted: payment is a social matter between two consenting adults at a public venue; the platform's job is honesty + a paper trail, not adjudicating dinner bills.

**Decision: implement Option (b).** It is the roadmap's stated launch-blocking slice ("launch-blocking only as a copy/expectation fix… option (b) is cheap and removes the integrity gap immediately"). Option (a) is recorded below as a future design with no tasks.

```sql
-- supabase/migrations/20260525121300_p10_reports_reason_category.sql
-- P10: relabel the pay setting as a NON-BINDING social convention.
-- No money moves. We only make pay-related abuse trackable by extending the P0 reports intake.

-- Closed-set categories for report triage (P8 moderation). 'payment_dispute' is the
-- pay-setting abuse channel: "they advertised a pay setting and acted in bad faith."
create type report_reason_category as enum (
  'harassment',
  'safety',
  'inappropriate_content',
  'no_show',
  'impersonation',
  'payment_dispute',
  'spam',
  'other'
);

alter table reports
  -- nullable for backward-compat with any P0-era rows; new writes set it (enforced in validators/API).
  add column if not exists reason_category report_reason_category,
  -- snapshot of itineraries.pay_setting at report time, so a later edit of the night
  -- cannot rewrite history of what was advertised. Reuses the P0 payment_preference enum.
  add column if not exists pay_setting_snapshot payment_preference;

-- A payment dispute is meaningless against a 'user' or 'message' alone — it must point at the
-- night (date_instance) or the locked pair (lock) the pay setting was attached to.
alter table reports
  add constraint reports_payment_dispute_targets_date
  check (
    reason_category is distinct from 'payment_dispute'
    or target_type in ('date_instance','lock')
  );

create index if not exists reports_reason_category_idx
  on reports (reason_category) where reason_category is not null;
-- RLS unchanged from P0: reporter-insert only, admin/service-role read (default-deny select).
```

```ts
// packages/business/src/pay-setting.ts
//
// Pay setting = a NON-BINDING social convention (Option b, P10 decision gate).
// It is a heads-up about the vibe, NOT a transaction. After5 moves no money for
// dates and makes no payment guarantee. These strings are the single source of
// truth for every surface (web today, native later) so the framing never drifts.

// Mirrors the P0 `payment_preference` enum: 'i_pay' | 'they_pay' | 'split'.
export type PaySetting = 'i_pay' | 'they_pay' | 'split';

// Spec §4 display labels.
export const PAY_SETTING_LABELS: Record<PaySetting, string> = {
  i_pay: 'I pay',
  they_pay: 'They pay',
  split: '50-50',
};

// The disclaimer shown wherever a pay setting renders. Deliberately explicit that
// it is not a guarantee and that the platform processes no payment.
export const PAY_SETTING_DISCLAIMER =
  'Just a heads-up about the vibe — not a guarantee. After5 doesn’t process any payment; sort the bill out together in person.';

export interface PaySettingDisclosure {
  label: string;
  disclaimer: string;
  /** Always false in Option (b). Kept explicit so a future binding tier is a deliberate change. */
  isBinding: false;
}

export function describePaySetting(setting: PaySetting | null | undefined): PaySettingDisclosure | null {
  if (!setting) return null;
  return {
    label: PAY_SETTING_LABELS[setting],
    disclaimer: PAY_SETTING_DISCLAIMER,
    isBinding: false,
  };
}

export function paySettingDisclosure(setting: PaySetting | null | undefined): string | null {
  return setting ? PAY_SETTING_DISCLAIMER : null;
}
```

```ts
// (supabase/migrations/20260525121300_p10_reports_reason_category.sql).

  'inappropriate_content',

  'impersonation',
  'payment_dispute',
  'spam',
  'other',
```

```tsx
// apps/web/components/PaySettingBadge.tsx
import { describePaySetting, type PaySetting } from '@after5/business';
import { cn } from '../lib/cn';

interface PaySettingBadgeProps {
  setting: PaySetting | null | undefined;
  className?: string;
  /** Compact (badge only, disclaimer in title) vs. full (visible disclaimer line). */
  variant?: 'full' | 'compact';
}

/**
 * Renders the night's pay setting as a NON-BINDING social convention (P10).
 * Copy comes from @after5/business so web + native stay identical. Never a promise.
 */
export function PaySettingBadge({ setting, className, variant = 'full' }: PaySettingBadgeProps) {
  const d = describePaySetting(setting);
  if (!d) return null;

  return (
    <div className={cn('flex flex-col gap-1', className)}>
      <span
        className="inline-flex w-fit items-center rounded-full bg-pink-100 px-2.5 py-0.5 text-sm font-medium text-pink-800"
        title={variant === 'compact' ? d.disclaimer : undefined}
      >
        {d.label}
      </span>
      {variant === 'full' && (
        <span className="text-xs text-gray-500">{d.disclaimer}</span>
      )}
    </div>
  );
}
```

## FUTURE / OPTIONAL — Option (a): binding payment via Stripe Connect (NO tasks)

> Documented for completeness. **Not built in P10.** Pursue only when a premium/marketplace tier justifies the regulatory + ops weight, and revisit the spec §4 "no penalty / renegotiable" intent (escrow contradicts it).

**When it's justified:** a paid tier where one party books/pays for a curated, higher-stakes experience (e.g., event tickets, a prix-fixe), and where a real financial commitment measurably reduces flaking *and* the volume covers compliance overhead.

**Sketch (design only):**
- **Stripe Connect (destination charges).** Payers add a card; the night's "payer" onboards as a connected account (KYC handled by Stripe). On `lock`, create a **PaymentIntent with `capture_method: 'manual'`** (an authorization hold), not an immediate charge.
- **Lifecycle ↔ state machine.** Tie capture/refund to P5 lock states: `locked` → hold placed; `completed` → capture (or release if the convention was "split in person"); benign `cancelled` → release the hold (honors §4 "without penalty"); `no_show`/`misconduct` → policy-driven capture or partial, routed through dispute moderation (P8).
- **New tables (future migration):** `payment_intents` (stripe id, lock_id, amount, status, capture/refund timestamps), `connected_accounts` (user_id ↔ stripe acct, onboarding state), `payment_disputes` promoted from a report category to a first-class adjudicated entity. All with RLS scoped to the two parties + service-role.
- **Webhooks:** a Supabase Edge Function verifying Stripe signatures and advancing payment state idempotently (mirror the P5 idempotency discipline).
- **Compliance you take on:** money-transmission posture, KYC on payees, refund/chargeback SLAs, tax reporting, PCI scope (mitigated by Stripe Elements/hosted), and dispute arbitration headcount.
- **Migration from (b):** the Option-(b) `payment_dispute` report rows become the training/seed data for whether escrow is worth it — measure dispute rate before investing.

This section intentionally has **no TDD tasks**; it is a future spec hook, not launch scope.
