# P4 Browse & Interest — Pre-Development Audit

Audited file: `docs/superpowers/plans/2026-05-25-p4-browse-feed.md`
Cross-referenced: spec (browsing/privacy/native), roadmap (Phase ordering + Risk Ledger), P0 (`browse_feed`, `swipes`, `date_instances`), P1 (preference columns + CHECKs), P3 (`browse_feed v2`, `convert_to_scheduled`, `itineraries.opener`), P5 (consumes `swipes`, seeds `queue_entries`).
Verdict: **Strong on the blind contract and the swipe path; ships with three blocking defects (a migration that will not apply, a cross-phase view collision that silently drops `is_seed`, and a leak-test that asserts the wrong oid) plus a structurally inert pagination model.** Do not execute as-is.

---

## 1. Blocking Issues (must fix before any code is written)

**B1 — The concierge seed UUID is not a valid UUID; Task 7's migration aborts the whole stack.**
`20260525130400_p4_feed_seed.sql` casts `'00000000-0000-0000-0000-0000000c0nc'::uuid` (lines ~663, 670, both `insert` and the `do $$` block). The final group `0000000c0nc` is **11 characters and contains `n`** (not a hex digit). Postgres raises `invalid input syntax for type uuid` at migration apply, so `supabase db reset` fails, the cold-start test never runs, AND **every later phase's `db reset` (P5, P6…) breaks** because this migration sits in the shared timeline. This is a copy-paste "leet-speak" UUID that was never compiled. Replace with a real fixed UUID (e.g. `00000000-0000-0000-0000-0000000c0fee` → still invalid; use all-hex like `00000000-0000-0000-0000-0000000c0n…` is impossible — pick `'00000000-0000-0000-0000-0000000c1dec'` or simply `gen_random_uuid()` stored in a seeded `app_config` row). Until fixed, **nothing in P4 runs**.

**B2 — P3's `browse_feed v2` lands AFTER P4 by timestamp and does not exist-check P4's columns; the view P4 built is overwritten and `is_seed` is silently dropped from the view.**
Migration ordering is purely lexical. P4 uses band `20260525130100` (`p4_browse_feed_geo` adds `is_seed` to the view). P3 uses band `20260526130800` (`p3_..._feed_v2`) — a **later** timestamp — and is a full `create or replace view browse_feed` that **omits `is_seed`** (confirmed: `grep is_seed` in P3 returns nothing). Roadmap critical path is `P0 → (P1,P2,P3) → P4`, i.e. P3 is *supposed* to land first, but the filenames invert that. Net effect depends on apply order, and it is contradictory either way:
  - If P3 applies last (as timestamps dictate), the final `browse_feed` has **no `is_seed`** and no `distance_m`. P4's Task 5 leak test still passes (it only checks for *absence* of identity), but any future consumer of the view loses the seed marker. P4's RPC reads `date_instances` directly so the *feed* still works — but the view is now a latent landmine: the plan's Self-Review claims "Task 3 evolves the view additively (still no identity)" which is **false after P3 reapplies it**.
  - If executed in roadmap order (P3 then P4), P4's `p4_browse_feed_geo` clobbers P3's `sound_title/sound_license/opener` columns that P3's own feed-v2 test asserts exist — **breaking P3's `p3_feed_v2.sql` test retroactively**.
There is no single ordering where both phases' view tests pass. Decide one owner of `browse_feed`'s final shape (recommend: P4's view migration must `select` P3's sound/opener columns too, OR P4 abandons the view entirely and documents that the RPC is the only feed reader). Pick one and make both phases' view definitions identical supersets.

**B3 — The leak test's RPC-signature check (Task 5, block 2) inspects `proargnames`, which does not contain OUT/return-table column names for a `RETURNS TABLE` function defined the way P4 writes it — the test gives false assurance.**
`browse_feed_for_viewer` is declared `RETURNS TABLE(... )`. In Postgres those table columns ARE recorded in `pg_proc.proargnames` (with `proargmodes='t'`), so the loop *can* see `creator_id` if it were an output column — but P4 never names an output `creator_id`, and the **real** leak risk is the *body* selecting `cp.full_name` etc. into a generically-named output column. The body guard (block 3) only greps for the literal substring `'di.creator_id,'` — it will **not** catch `cp.full_name`, `cp.clear_photo_url`, `pl.name` (venue name), or `creator_id` selected without a trailing comma (e.g. last in list, or aliased). The "trust-critical assertion" is brittle string-matching, not a behavioral test. Add a **behavioral** leak test: insert a creator with a known `full_name`/`clear_photo_url`, call the RPC as a viewer, and assert the returned row's text fields never equal those PII values. Structural column-name checks are necessary but not sufficient.

**B4 — Pagination is structurally inert: the deck never advances the cursor, so a user with >20 compatible nights can never see night #21, and the keyset cursor is unsorted-compatible with the ORDER BY.**
The RPC orders `by di.is_seed asc, di.id asc` but the cursor predicate is `di.id > p_cursor` — this keyset is **only valid if the sole sort key is `di.id`**. Because `is_seed` is the primary sort key, paging by `id > cursor` will **interleave/skip** rows: page 1 returns real nights ordered by id; if the last real night's id is high, page 2 (`id > that`) skips all seed nights with lower ids, then on a later page re-surfaces nothing. Worse, the **web client never paginates at all**: `page.tsx` fetches `{ limit: 20, cursor: null }` once; `SwipeDeck` only does `setCards(c => c.slice(1))` and shows "No more nights" at zero — there is no `loadMore`, no cursor state, no refetch. Result: **hard cap of 20 nights per session**, then a dead "No more nights right now" even when hundreds are compatible. Either implement cursor-following in the deck (track last id, refetch when buffer low) or change the order to `(is_seed, id)` keyset with a composite cursor. As written, "feed pagination at scale" is unimplemented.

**B5 — `distance_m` is in the RPC output but distance is measured from the viewer's *city centroid*, not the viewer — and the card claims "4.2 km away," which is false and an identity/abuse vector.**
`ST_Distance(di.geo, v_geo)` where `v_geo = cities.centroid` of the viewer's primary city. Every viewer in Kelowna gets the **same** distance to a given venue. The card renders `"${(distance_m/1000).toFixed(1)} km away"` — presenting centroid-to-venue distance as personal proximity is misleading, and because it's deterministic per city it leaks nothing useful yet still claims precision it doesn't have. Either (a) bucket to coarse labels ("~5 km", "in your area") to match the anti-triangulation intent the plan states for `geo`, or (b) drop the meter display until native passes a real viewer point. Shipping a fake "4.2 km away" undermines the trust the whole blind/privacy story is built on.

## 2. Broken / Incomplete User Flows

- **Right-swipe on a seed (concierge) night is a dead end.** Task 7 says a right-swipe on a seed night "routes to a concierge-handled flow … for P4 it simply records the swipe and shows a 'we'll line up a real match' confirmation." **No such confirmation exists in the code.** `SwipeDeck.swipe()` does the identical `slice(1)` for seed and real nights; there is no branch on `top.is_seed`, no "we'll line you up" message. The user right-swipes a curated night and gets… the next card, silently. The promised cold-start payoff is absent. (And see C1: P5 has no handler for the swipe that lands.)
- **Empty/exhausted state shows simultaneously with a deck that thinks it's empty.** `feedTier` is computed once on the server from the initial 20. If `tier==='seed_only'`, the page renders `<EmptyFeedState variant="seed_only" />` **above** a live `SwipeDeck` of seed cards — fine. But once the user swipes through all seed cards, `SwipeDeck` shows its own "No more nights right now" *below* the seed_only banner — two competing empty messages, no CTA on the inner one. The exhausted CTA ("Create a night") only appears on initial load when `cards.length===0`, never after the user swipes the deck to empty in-session. The most common exhaustion path (swipe everything) lands on the dead inner string, not the CTA.
- **No loading or error state anywhere.** `page.tsx` `await browseFeed(...)` with no try/catch: if the RPC errors (e.g. viewer has no profile row — see E2), the RSC throws and the user gets Next's error boundary, not a feed. `SwipeDeck.swipe()` swallows fetch failures (`finally` advances regardless) so a failed swipe still removes the card — the interest is **lost silently** and unrecoverable (the card is gone from the deck). No spinner, no retry, no toast.
- **Signed-out users get a different feed contract than the RPC.** `page.tsx` shows "Sign in to browse nights" for no user, but the *spec/roadmap* describe the blind feed as the public discovery surface. The RPC `return`s empty for `v_id is null` (so anon gets nothing), and the view is granted to `anon`. The plan never resolves whether logged-out browsing is a product goal; if it is, there's no anon path; if it isn't, the `grant select … to anon` on the view is dead surface.

## 3. Missing Backend / API / Schema

- **No "similar nights" / consolation query**, though the roadmap Risk Ledger assigns "'Similar nights' consolation has no query" to **P4/P5**. P4 ships nothing for it. After a left-swipe or exhaustion there is no reco path.
- **No re-fetch endpoint for pagination** (see B4). `browse_feed_for_viewer` accepts a cursor, but no route/server-action exposes a "next page" call to the client; only the initial RSC fetch exists.
- **`dealbreakers text[]` (P1 Task 4) is never read by the filter.** P1 explicitly adds `profiles.dealbreakers` "that feed the Phase-4 compatibility pre-filter." P4's RPC reads gender/age/distance only. Either P4 must consume dealbreakers or the plan must explicitly defer them with a reason — right now it's a silent dropped requirement spanning the P1↔P4 seam.
- **Verification is not gated in the feed.** The filter checks `cp.dating_enabled` but not `cp.verification`. P5's demand hint counts **verified-only** for honest social proof; the feed surfaces unverified creators' nights. A swiper can express interest in an unverified ghost. At minimum decide whether the feed is verified-only (the spec's "Verified · New" framing suggests trust gating).

## 4. State / Data Lifecycle Gaps

- **No data lifecycle for seed nights.** Concierge `is_seed` instances are `now()+interval '7 days'`. After 7 days `starts_at` is in the past but `status` is still `'seeking'` — the feed (which filters only `status='seeking'`, never `starts_at > now()`) will **show stale, past-dated seed nights forever**. There is no job to re-roll or expire them (P2/P5 own jobs but P4 created the rows with no expiry contract). Same bug applies to **all** real nights: the feed never filters `starts_at > now()`, so any past `seeking` instance keeps showing. This is a missing `where di.starts_at > now()` in both the view and the RPC.
- **`record_swipe` allows swiping a night whose `starts_at` has passed** (it only checks `status='seeking'`). Combined with the above, users swipe dead nights.
- **No swipe revocation lifecycle beyond direction flip.** Idempotent re-swipe updates direction — good — but there's no "unswipe" (remove interest), and `record_swipe` has no path to delete. P5 reads right-swipes into `queue_entries`; a user who right-swiped then wants out has no mechanism in P4.

## 5. Cross-Phase Seam Breaks

- **C1 (seam P4→P5): the seed-night swipe has no consumer.** `grep` of P5 for `is_seed`/`concierge`/`seed` returns **nothing**. P5's `match_ingest_interest` blindly seeds `queue_entries` from all right-swipes, including swipes on concierge `is_seed` nights — so a real user becomes an "interested candidate" on a **concierge-owned** night, and the concierge (a fake profile with permissive prefs) is now expected to shortlist/offer via P5's creator flows. There is **no concierge actor** to run those flows. The "we'll line up a real match" promise has no implementing phase. This is the single biggest product hole: cold-start generates interest that dead-ends.
- **C2 (seam P0/P4/P3 on `browse_feed`):** three phases redefine the same view with divergent columns and inverted timestamps (see B2). State ownership of `browse_feed`'s final shape is undefined.
- **C3 (seam P3→P4 on geo):** P4 Task 2 adds `date_instances.geo` and a `before insert/update of venue_id, city_id` trigger; P3 Task 7's `convert_to_scheduled` RPC inserts `date_instances` with `venue_id`. Ordering: P3 (`20260526…`) applies **after** P4 (`20260525…`), so when P3's convert RPC runs the geo trigger exists — OK. But P4 Task 4 **redefines** `set_date_instance_geo()` (to respect explicit geo). If P3's later migration or any P3 test inserts a `date_instance` expecting the *original* trigger behavior, behavior differs by apply order. The trigger is now owned by two phases. Document P4 as the owner.
- **C4 (seam P4→P1):** the filter's "permissive on missing prefs" decision (empty `gender_preferences`/null `age_pref` ⇒ pass) assumes P1 makes these required. P1's zod requires `gender_preferences.min(1)` and CHECKs `age_pref` bounds — but those guard *writes*, and the column DEFAULT for `gender_preferences` is `'{}'` (P0) with no NOT NULL on `age_pref`. A user who set `dating_enabled=true` before completing the prefs step (or via the age-gate trigger path) is **shown to everyone**. The permissive default is an **identity/abuse vector**: a half-onboarded creator's nights leak into every feed regardless of mutual fit. Pre-filter must require completed prefs (e.g. exclude creators with empty prefs from the feed, not pass them).

## 6. Privacy / Identity-Leak / Abuse Risks

- **The blind contract on the RETURN PATH is solid** (RPC selects only feed columns; view has no identity; api-client re-parses through `FeedCardSchema` stripping extras). This is the plan's strongest part. But:
- **Venue name leak via `places.name` is not tested.** The RPC selects `pl.neighborhood` — correct — but the leak test (B3) never asserts the exact venue *name* or *address* is absent, and a one-character edit selecting `pl.name` would pass all three Task-5 checks. The spec's pre-lock privacy is specifically "no exact venue."
- **`distance_m` precision** (B5) is a soft triangulation surface the plan flags for `geo` but then re-introduces via meters.
- **Fake-date harvesting (roadmap: honeypot, assigned P5):** P4 writes swipes; the swiper's profile becomes visible to the creator at P5 shortlist. But **P4 lets anyone create unlimited seed-like real nights** (no rate limit here; P3/P8 own it) and there's no velocity limit on `record_swipe` — a swipe-farm can right-swipe every night to force disclosure pools. P4 should at least note the abuse surface it opens; it's silent.
- **Block enforcement is one-directional in time.** The RPC excludes blocked pairs at read time — good — but a swipe recorded *before* a block persists in `swipes` and P5 reads it. P4's `record_swipe` does not check `blocks`. Edge case: block, then the pre-block swipe still seeds P5's queue.

## 7. Mobile / Ambient / Real-Time Concerns

- **AmbientPlayer web fallback is well-handled** (gesture-gated, `.catch`, text caption, no autoplay) — matches spec §10 and the roadmap's "graceful no-audio fallback." Good.
- **But the `autoPlay` prop has no platform wrapper in P4.** The component takes `autoPlay` "true only on native via the platform wrapper" — that wrapper does not exist in any phase referenced. It's a forward-declared seam with no owner; flag it so native (later) knows to build it.
- **No teardown of audio between cards.** `AmbientPlayer` is rendered fresh per card via `FeedCard`, but `SwipeDeck` renders only `cards[0]`; on swipe the `<audio>` unmounts — React stops it. Acceptable, but rapid swiping while playing can leak a still-loading audio element; `preload="none"` mitigates. Minor.
- **`<audio loop>` with `preload="none"` and no `muted`** means even the toggle requires a user gesture (fine on web) but on the *first* card the user must tap twice (once to focus the page, once to play) on some mobile browsers. Untested.

## 8. Scalability / Performance

- **The pre-filter RPC is O(all seeking instances) per call with multiple correlated NOT EXISTS subqueries** (`blocks`, `swipes`) and a per-row `ST_Distance`. At low volume fine. At scale the `swipes` anti-join (`not exists … swiper_id=v_id`) over a user with thousands of historical swipes, plus `ST_DWithin` over an un-partitioned `date_instances`, with `order by is_seed, id` (not index-aligned with the geo GiST), forces a sort of the full compatible set every page. The `date_instances_geo_gist` index helps `ST_DWithin` but not the ORDER BY. No covering index for the filter's hot path (`status, creator_id`). The plan claims "keyset … deterministic for v1" but the keyset is broken (B4) and the ordering can't use the GiST index. **Ranking is absent** — feed is id-ordered, so newest content is buried behind lowest-uuid content forever (uuid v4 is random, so it's effectively arbitrary-stable, not recency). Roadmap assigns feed ranking refinement later, but "id asc" means a compatible night created today may never surface above older inventory.
- **`force-dynamic` RSC + per-viewer RPC** = no caching, full DB round-trip per feed view. Expected for personalization; just note the RPC must be fast because nothing caches it.

## 9. Contradictions / Spec-Plan Misalignments

- **Self-Review claims (line ~1126) "Task 3 evolves the view additively (still no identity)" and lists it ✅** — contradicted by B2: P3's later `create or replace view` is NOT additive over P4's and drops `is_seed`. The ✅ is unearned.
- **Self-Review claims the leak test proves the contract three ways** — block 2 (`proargnames`) and block 3 (substring) are weak/incorrect (B3); the claim overstates assurance.
- **Plan says seed swipe "shows a 'we'll line up a real match' confirmation"** (Task 7 prose) — no such UI exists in Task 9 code (Section 2). Prose ↔ code contradiction.
- **Plan says distance "measured venue→viewer-city-centroid"** and separately renders "km away" as if personal — internally inconsistent precision story (B5).
- **`FeedCardSchema.time_window_start` is `z.string().datetime()`** but the RPC returns `timestamptz` and the supabase-js client serializes it as e.g. `2026-06-01T19:00:00+00:00` — `z.string().datetime()` by default rejects timezone offsets other than `Z` unless `{ offset: true }`. The Task-1 unit test uses `…Z` and passes, but **real RPC output may fail `FeedCardSchema.parse` at the api-client boundary**, throwing on every real feed load. Verify the serialization format; add `.datetime({ offset: true })`.

## 10. Top Priorities (ranked)

1. **B1 — Fix the invalid concierge UUID.** One-line blocker that prevents `db reset` and breaks the entire downstream migration timeline. Trivial fix, catastrophic if missed.
2. **C1 — Define the seed-night swipe consumer (P4↔P5 seam).** The cold-start mechanic generates interest that has no handler; the "we'll line you up" promise is unimplemented across all phases. Either build a real concierge resolution path or change seed nights to a non-swipeable informational card. This is the product-integrity hole.
3. **B2/C2 — Resolve `browse_feed` ownership across P0/P3/P4.** Inverted timestamps mean one phase's view test must fail; pick a single superset definition (sound + opener + is_seed + no identity) and make P3 and P4 write the identical view. Then fix the brittle leak test (B3) with a behavioral PII assertion.

Runner-up (would be #4): **B4 — implement real cursor pagination** (current 20-night hard cap) and **time-filter the feed** (`starts_at > now()`) so stale/past nights stop surfacing.
