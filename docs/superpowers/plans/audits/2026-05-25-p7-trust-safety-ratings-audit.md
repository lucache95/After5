# P7 — Trust, Safety & Ratings — Pre-Build Audit

Auditor stance: paranoid principal engineer. Assume smart authors moving too fast. Safety bugs here are life-safety. Verdict below is about whether *executing this plan as written* yields a working, abuse-resistant safety system that actually wires to the rest of the product (P0/P2/P5/P6/P8). The internal craftsmanship is high; the **cross-phase seams are broken in ways that silently disable the two highest-stakes features** (the enforcement ladder and the moderation/dispute loop).

**Overall score: 5/10 — DO NOT EXECUTE AS WRITTEN.** Self-contained P7 SQL/TS is well-built and TDD'd, but the plan ships features that are dead-on-arrival once P2 and P8 land, plus its own test fixtures don't run against the real schema. Roughly 8–10 hours of seam + fixture fixes before it's executable and actually enforces what it claims.

Counts: **6 BLOCKERS · 9 MAJOR · 11 MINOR · 7 QUESTIONS**

## 1. Critical Blockers (ship-stoppers — feature is dead, data corrupts, or migrations fail)

**B1 — The enforcement ladder is enforced NOWHERE. `can_enter_lock_flow` has zero callers.**
D4's table claims each rung is "enforced where": cooldown → "offer-accept RPC checks", reconfirm → "accept-RPC flag", throttle → "P4/P5 read `standing`", locked_ban/suspended → "all RPC guards reject". I read P5's `match_accept_offer` (lines 834–930) and `match_make_offer` (642+): **neither references `can_enter_lock_flow`, `standing`, `reliability`, `cooldown`, `reconfirm`, or `locked_ban`.** P7 *defines* `can_enter_lock_flow(uuid)` and grants it, but nothing calls it, and P7 explicitly does not (cannot) modify P5. Result: a `cooldown`/`locked_ban`/`suspended` user can create and accept locks freely. The fast circuit-breaker — the entire point of D4 in a thin market — is a no-op. This is the single most damaging gap: the plan's Self-Review marks the ladder ✅ but it is functionally absent.

**B2 — `evaluate_standing` and `can_rematch` query `reports.status='actioned'`, a value P8 deletes.** P8 Task 3 (`20260525130200_p8_reports_lifecycle.sql`) rewrites `reports.status` from free-text into the `report_status` enum `('open','triaged','investigating','escalated','resolved','dismissed')` and **migrates `'actioned'` → `'resolved'`** (status) with the verdict moved to a separate `resolution='actioned'` column. After P8 lands, `where status='actioned'` matches **zero rows forever**. Consequences: (a) `evaluate_standing`'s safety-report rungs (`locked_ban` for 1 upheld safety report, `suspended` for 2) never fire; (b) `can_rematch` never treats an upheld safety report as a rematch bar — **a confirmed harasser can rematch their victim** as long as no `blocks` row exists. P8 keeps `'actioned'` only as a `resolution` code on a `'resolved'` row; P7 reads neither. Because P8 sorts after P7 in migration order (same timestamp, `_p8_` > `_p7_`), the columns P7 reads are *gone* by reset time. Safety-critical silent failure.

**B3 — `file_report` inserts `status='reviewing'`, which is not a valid enum value after P8.** D2/Task 10's `file_report` does `... status) values (..., case when v_safety then 'reviewing' else 'open' end)`. P0 allowed `'reviewing'` as free text; P8's `report_status` enum has **no `'reviewing'`** (it's `'investigating'`). After P8, every safety `file_report` call (and the `submit_rating` serious-flag insert at Task 2, and the `respond_safety_checkin` SOS insert at Task 11 which also writes `'reviewing'`) throws `invalid input value for enum report_status: "reviewing"`. The block_user-adjacent and SOS paths that write reports all break. This is a hard runtime failure on the most safety-critical code paths.

**B4 — `enqueue_job` signature & `jobs` schema collide head-on with P2; jobs silently never run or inserts fail.** P2 (the real owner) defines `jobs` with columns `job_type` (an **enum**), `run_after`, `status`, `attempts`, `dedup_key`, and `enqueue_job(job_type, timestamptz, uuid, uuid, uuid, uuid, jsonb, text)` (8 args, `job_type` enum first). P7's bridge creates `jobs(kind text, payload, run_at)` and `enqueue_job(text, jsonb, timestamptz)`. When P2 is present: (a) `create table if not exists jobs` is a no-op, so P7's trigger inserts `kind`/`run_at` into a table that has `job_type`/`run_after` → column-does-not-exist / NOT-NULL failure on every lock activation; (b) P7's `create or replace function enqueue_job(text,jsonb,timestamptz)` does **not** replace P2's (different arg types = different overload), so two `enqueue_job` overloads coexist and P7's callers resolve to its own text-arg version, inserting nothing P2's runner will ever claim (P2 claims by `job_type`/`run_after`). Worse, P7's job *kinds* (`safety_checkin`, `rating_window_close`, `day_of_reconfirm`, `safety_alarm_notify`, `safety_escalation_notify`) are not in P2's frozen `job_type` enum — so even a corrected insert raises `invalid input value for enum`. The safety check-in, rating-window-close, and reconfirm timers **never fire in production**. This makes D6's "silence is escalation" promise vacuous and B2-adjacent (no rating_window_close → lone retaliatory ratings hide forever, defeating D2).

**B5 — Every P7 SQL test fixture fails: `itineraries` requires NOT NULL `inputs`/`stops` and `user_id` FKs to `auth.users`.** All P7 tests do `insert into itineraries (id, user_id) values (gen_random_uuid(), cre)`. The real `itineraries` table (repo `20260419193959_initial_schema.sql`) has `inputs jsonb not null` and `stops jsonb not null` with **no defaults**, and `user_id references auth.users(id)` — but P7 fixtures insert a `profiles.id` and never create an `auth.users` row (the plan says "FKs point at `profiles`, not `auth.users`"). So every fixture insert throws either a NOT-NULL violation on `inputs`/`stops` or an FK violation on `user_id`. **Not one P7 SQL test can pass as written** — the TDD loop is broken at step 1 for Tasks 2, 4, 5, 6, 8, 9, 10, 11, 12. (P0 may rework `itineraries`, but P0's own date_instances test inserts via `itineraries i ... where i.user_id=cre`, implying P0 also assumes a profiles-FK'd, defaulted itineraries — a P0-vs-repo contradiction P7 inherits and must resolve, not ignore.)

**B6 — The disputed-no-show / moderation dispute loop is fully orphaned across the P7↔P8 seam.** P7's `adjudicate_no_show` resolves a contradicted no-show by writing a **`reports` row** with `reason='disputed_no_show'` and setting `match_ratings.disputed=true, weight=0`. P8 builds a dedicated **`disputes`** table "for contested no-show/rating outcomes from P7" and a `rule_dispute()` RPC — but (a) **P7 never inserts a `disputes` row**, so P8's dispute queue is always empty; (b) P8's `rule_dispute()` only flips the dispute row + writes a moderation_action — it **never calls `recompute_reliability`, never clears `match_ratings.disputed`, never calls `evaluate_standing`.** So when a moderator overturns a disputed no-show, the accused's score is **never restored** and the liar's standing is **never updated**. The "a human resolves the conflict" promise in D3 has no machinery on either side. A `disputed=true, weight=0` rating is frozen out of the score *permanently* with no path back. This is both a safety gap (real no-shows get permanently buried as "disputed") and a fairness gap (false-disputed users stay penalized... actually they stay *un*-penalized, which is the abuse vector: a no-show simply needs the *victim* to have checked in to escape the penalty forever — see A1).

## 2. Missing / Broken Backend (actions with no implementation, orphaned components)

**M1 — Mandatory day-of reconfirm for `reconfirm_required` users has no enforcement.** D4 says rung 4 forces "every future lock forces a mandatory day-of reconfirm (P2 job + accept-RPC flag)." Task 12 schedules a *default* `day_of_reconfirm` job for *all* locks, but nothing reads `standing='reconfirm_required'` to make reconfirm **mandatory** (i.e., auto-cancel the lock if not reconfirmed). P5's `match_reconfirm` exists only for the auto-roll path, not for a standing-driven gate. The rung is cosmetic.

**M2 — `throttled` standing affects nothing.** D4 rung 3 says "feed rank suppressed + queue priority lowered (P4/P5 read `standing`)." P5/P4 do not read `standing` (grep-confirmed for P5). No P7 task adds the read, and P7 can't modify P4/P5. Dead rung.

**M3 — `rollover_frozen` flag is written by P7, read by nobody.** P7 adds `locks.rollover_frozen` and sets it `true` in `block_user` and `file_report`. P5's `match_auto_roll` (the §7.6 logic) checks **`reports` directly** (`target_type='date_instance' and status<>'dismissed'`) and the time cutoff — it never reads `locks.rollover_frozen`. So `block_user` (which sets `rollover_frozen` but writes **no report**) does **not** actually freeze rollover via the path P5 uses. And `file_report` on a `lock` sets `rollover_frozen` but P5 keys its freeze on `target_type='date_instance'`, not `'lock'` — so a report filed against the lock (the natural target for "the date went wrong") does **not** freeze the roll either. The freeze only works by accident when a report happens to be `target_type='date_instance'`.

**M4 — `submit_rating` is grantable to `authenticated` but takes `p_rater` as a parameter — trivially spoofable.** `submit_rating(p_lock_id, p_rater, p_ratee, ...)` is `security definer` and granted to `authenticated`, and it trusts `p_rater` rather than `auth.uid()`. Any authenticated user can submit a rating *as someone else* for any lock they aren't part of by passing another user's id as `p_rater` (the guard only checks `p_rater` is a party — not that the caller *is* `p_rater`). Same flaw in `record_attendance_checkin`, `respond_safety_checkin` (takes `p_user`), and `block_user`/`file_report` (take `p_blocker`/`p_reporter`). These must derive the actor from `auth.uid()`, not a parameter. As written, the anti-retaliation, check-in proof, SOS, and block systems are all impersonable.

**M5 — No path writes `match_ratings.revealed_at` at window close in the standalone P7 world.** D2 relies on the `rating_window_close` P2 job to flip lone ratings to revealed. Task 12 *enqueues* that job, but the *handler* lives in P2 and is not in P2's frozen job_type enum (B4). There is no P7 RPC like `close_rating_window(lock_id)` that the handler would call, and P2's plan doesn't define one. So even with P2 present, "window closes → lone rating reveals" has no implementation on either side — a non-responding counterparty hides a bad review indefinitely (the exact thing D2 promises to prevent).

**M6 — Emergency contact notification has no actual send.** D6/Task 11 sets `contact_notified_at=now()` and enqueues `safety_alarm_notify`/`safety_escalation_notify` jobs, but (a) those kinds aren't in P2's enum (B4) and (b) no SMS/voice channel is specified — P2's notify path is push/web-push/email to the *user's* devices, not an outbound SMS to a third-party phone. `emergency_contact.phone` is never dialed/texted by any defined component. Setting `contact_notified_at` is a lie until a real outbound channel exists.

**M7 — `can_enter_lock_flow` ignores `reconfirm_required` and `throttled` and `warned`, and returns `true` on missing profile.** Even if a caller existed (B1), the guard only rejects `locked_ban`/`suspended`/active-`cooldown`. It silently `coalesce(..., true)` for a missing row — fail-open on a safety guard. A nonexistent/half-provisioned profile can enter the lock flow.

**M8 — No `unblock` / block-removal path, and `can_rematch` is permanent.** `block_user` is one-way. There's no RPC to unblock, and `can_rematch` treats any historical block as a permanent bar. Combined with "upheld safety report" (broken per B2) this is the *only* working rematch bar — and it's irreversible with no admin override surfaced in P7.

**M9 — `adjudicate_no_show` re-runs on every check-in but can't *un-penalize* a corroborated no-show, and double-counts standing.** If A rates B no-show (neither checked in → weight 0.5, penalty applied, standing recomputed), then B later check-ins late within the window via the Edge Function, Task 13 re-calls `adjudicate_no_show`, which flips to `disputed=true, weight=0` and recomputes — good. But if A *also* had proof and B then checks in, the state oscillates corroborated↔disputed depending on call order, and each call fires `recompute_reliability`→`evaluate_standing`, which can insert duplicate `user_sanctions` rows and re-notify on every recompute (no dedup on standing-unchanged is fine, but `evaluate_standing` is called from both `recompute_reliability` and `adjudicate_no_show`'s loop → N recomputes per adjudication).

## 3. Data Model Integrity (relationships, constraints, impossible states)

**D-1 — `match_ratings.weight` is overloaded with two incompatible meanings.** Task 1 documents `weight` as "adjudication multiplier (1.0 verified, 0.5 unverified no-show)." `adjudicate_no_show` sets it to `0.00` for disputed. But `recompute_reliability` *excludes* `disputed=true` rows entirely (`where ... disputed=false`), so the `weight=0` is redundant for disputed rows and the `weight` column never carries the *recency×adjudication* product the TS oracle expects — the TS `RatingInput.weight` is the adjudication weight only, recency is applied separately. Consistent here, but the `disputed` filter + `weight=0` double-guard is a latent contradiction if a future query forgets the `disputed=false` predicate.

**D-2 — `reports` has no unique constraint, so `adjudicate_no_show` and SOS spam duplicate reports.** P0's `reports` has no natural key. `adjudicate_no_show` uses `on conflict do nothing` (the plan's own note flags this won't work — there's no constraint to conflict on). Every re-adjudication (every check-in) opens a *new* `disputed_no_show` report. The SOS path opens a new `safety_sos` report on every `respond_safety_checkin('alarm')`. T&S queue floods with duplicates. The fallback `if not exists` guard is only suggested, not specified in the migration.

**D-3 — `safety_checkins.due_at` semantics vs the `awaiting` partial index drift.** The escalation Edge Function selects all `status='awaiting'` and filters `isOverdue` in TS. The partial index `where status='awaiting'` helps, but there is no upper bound — a check-in stuck `awaiting` forever (user never opened the app, P2 push failed) is re-scanned every sweep indefinitely. No `missed` terminal transition is wired (the enum has `'missed'` but no code sets it).

**D-4 — `user_sanctions` (P7) vs `suspensions` (P8) are two competing sources of truth for "can this account act."** P8 explicitly calls `suspensions` "the single source of truth for can this account act" and gates via `is_suspended()`. P7 writes `profiles.standing` + `user_sanctions` and gates via `can_enter_lock_flow`. Neither reads the other. A P8 moderator `temp_suspend` does **not** set `profiles.standing='suspended'`; a P7 auto-`suspended` does **not** create a `suspensions` row. Two ladders, no reconciliation — a user can be P8-suspended but P7-`good` (and vice versa), and which one a given RPC honors is accidental.

**D-5 — `profiles.standing_until` lift is never executed.** `evaluate_standing` sets `standing_until` for `cooldown`/`locked_ban` but nothing *lifts* the standing when the clock expires. `can_enter_lock_flow` checks `cooldown and standing_until > now()` inline (so cooldown self-lifts at read time), but `locked_ban` is checked as `standing in ('locked_ban')` with **no `standing_until` check** — so a locked_ban is **permanent** until a new `evaluate_standing` happens to downgrade it, which it can't (monotone-within-window prevents auto-downgrade; only "the clock lifts" — but no clock job exists). Dead users stay banned forever.

## 4. Cross-Phase Seam Failures (the integration contracts)

**S-1 (BLOCKER, =B2/B3) — P8 reports status enum migration breaks P7's `'actioned'` reads and `'reviewing'` writes.** Covered in §1. The seam is bidirectional and silent.

**S-2 (BLOCKER, =B4) — P2 jobs schema/enqueue contract mismatch.** P7's "minimal jobs contract" is *not* compatible with P2's actual `jobs` (enum `job_type`, `run_after`, frozen kinds). The "no-op if P2's exists" claim is false: a `create table if not exists` against an existing different-shaped table leaves the *wrong* columns, and P7's inserts/overload diverge. This needs P2's exact column names and an ALTER to P2's `job_type` enum adding P7's kinds, or P7 must not own `enqueue_job` at all and instead call P2's signature.

**S-3 (MAJOR) — P7 reimplements lock cancellation instead of calling P5's `match_cancel_lock`.** `block_user` does a raw `update locks set status='cancelled', cancel_reason='safety', rollover_frozen=true`. P5 owns `match_cancel_lock(actor, lock_id, reason, idem_key)` which is the *only* sanctioned path (it deactivates `lock_participants` via the `sync_lock_participants` trigger to free the time window, handles the §7.6 freeze, audits, and is idempotency-keyed). P7's raw update **bypasses participant deactivation** (the GiST window stays blocked → the blocked user can't book a replacement date for that slot), skips audit semantics P5 guarantees, and won't trip P5's freeze logic (which reads `reports`/cutoff, not `rollover_frozen` — M3). Name does not match the audit's hypothesized `match_cancel_lock`; P7 doesn't call it at all.

**S-4 (MAJOR) — P5's swipe/offer block guards duplicate, and disagree with, `can_rematch`.** P5 already has inline `blocks`-pair guards on `match_make_offer` and the queue-enqueue path. P7 adds a *separate* `swipes` BEFORE-INSERT trigger calling `can_rematch`. Two guards, two definitions: P5's checks only `blocks`; P7's `can_rematch` also checks upheld safety reports (broken per B2). They will diverge (e.g., P5 lets an offer through that P7's swipe trigger would have blocked, or vice versa). Also P7's trigger references `new.creator_id` on `swipes` — that column exists (denormalized in P0), good — but a `before insert` `raise exception` on swipe is a poor UX signal vs P5's structured `OFFER_CONFLICT` returns; clients won't know why the swipe 500'd.

**S-5 (MAJOR) — P6 `chat_threads` column assumption is wrong.** `block_user` dynamic SQL updates `chat_threads set revoked_at` keyed on `(user_a, user_b)`. P6's actual `chat_threads` has **`creator_id`/`candidate_id`** (and a `status` enum `open|closed|archived|frozen` with no `revoked_at` column — freeze is `status='frozen'`, see P6 Task `block_freeze_archive`). So P7's reveal-revocation either no-ops (column/`to_regclass` guard hides the failure) or errors. The plan's own caveat admits "adjust when P6 lands," but it ships a guess that is concretely wrong against the sibling plan that exists. Also P6 *itself* implements block propagation (P6 Task 6 `block_freeze_archive`) — so block→chat-freeze is **double-owned** by P6 and P7 with different mechanisms.

**S-6 (MAJOR) — Disputes loop orphaned (=B6).** P7 writes `reports(reason='disputed_no_show')`; P8 expects `disputes` rows; `rule_dispute` never calls back into P7. No component bridges them.

**S-7 (MINOR) — `profiles.verification` vs `verifications` table.** `safety_center` reads `profiles.verification` (the enum column, exists in P0) — fine — but the spec's "Verified · New" is a function of `verification='verified' AND reliability_score IS NULL`; safety_center returns them as two raw fields and never composes the "· New" label. Client must replicate the rule (logic leak out of `business`).

**S-8 (MINOR) — `audit_log` requirement not met by most P7 RPCs.** Conventions: "every status mutation must reach `audit_log`." `submit_rating`, `block_user` (lock cancel!), `file_report`, `respond_safety_checkin`, `evaluate_standing` write `user_sanctions` but **not** `audit_log`. Only `user_sanctions` captures standing changes; lock cancellation via `block_user` reaches neither `audit_log` nor P5's audit triggers (raw UPDATE). Safety-critical mutations are partially unaudited.

## 5. Auth / RLS / Security Gaps

**R-1 (MAJOR) — Actor-id-as-parameter impersonation across all write RPCs (=M4).** `submit_rating`, `record_attendance_checkin`, `respond_safety_checkin`, `block_user`, `file_report` all trust a passed-in actor id and are granted to `authenticated`. Must use `auth.uid()` and ignore/validate the param. As written, a user can rate, check in, SOS, block, and report *as anyone*.

**R-2 (MAJOR) — `attendance_checkins` insert RPC is `service_role`-only but the Edge Function trusts client-claimed `lock_id` to find the venue.** Good that distance is server-computed. But the Edge Function fetches `date_instance_id` from `locks` by client-supplied `lock_id` with the *admin* client (RLS-bypassing) and never verifies the JWT user is a party to that lock before computing/storing (the DB RPC does check party membership — OK — but the function leaks venue coordinates for *any* lock id to *any* authenticated caller via the response `distance_m`, a location oracle). An attacker can binary-search a venue's coordinates for arbitrary locks.

**R-3 (MINOR) — `safety_center(p_user)` takes a target user param and is granted to `authenticated`, with no `p_user = auth.uid()` check.** It's `security definer stable` and returns emergency-contact-on-file, block list, standing, active locks + venues for **any** `p_user`. Any authenticated user reads anyone's safety center, including their active-lock venue + start time — a stalking vector. Must pin to `auth.uid()`.

**R-4 (MINOR) — `user_sanctions` RLS lets the sanctioned user read their own sanction reason string** which embeds `format('auto: no_shows=%s reliability=%s safety=%s', ...)` — leaks the internal reliability number and exact no-show count the product deliberately hides (score is null'd as "Verified · New" below MIN_RATED; here it's exposed verbatim).

**R-5 (MINOR) — Edge Functions read `SUPABASE_SERVICE_ROLE_KEY` and `attendance-checkin` is `verify_jwt=true` but still constructs an admin client** that bypasses RLS for the venue lookup and the `adjudicate_no_show` re-run; any input-validation miss = full table access. Acceptable pattern but the re-adjudication call from a user-triggered function lets a user force re-scoring of a counterparty at will (DoS / score-thrash via repeated check-ins).

## 6. Abuse Vectors & Safety Edge Cases

**A1 (CRITICAL abuse) — "Victim must have checked in" inverts the no-show penalty into a no-show *shield*.** D3 rule: if B (the accused) has a valid check-in, A's no-show claim is disputed and **no penalty applies, score unaffected pending human resolution** — and B6 shows the human resolution never feeds back. So a serial no-show only needs to *physically arrive, check in at the venue, and leave* (or spoof a check-in) to make every "you didn't show" claim against them permanently `disputed=true, weight=0`. They get the no-show effect (ditch the date) with zero reliability cost. The geofence "proof" protects the *accused*, not the *wronged party*. The asymmetry is backwards for the thin-market harm the ladder targets.

**A2 (MAJOR) — Geofence spoofing / GPS-off / venueless dates.** The Edge Function trusts client lat/lng (only distance is server-side from those coords). A rooted/jailbroken device or browser dev-tools trivially fakes coordinates at the venue centroid → fake "proof" → A1 shield. The plan's "safe-by-default" note (no coords → unverified 0.5) handles *absence*, not *forgery*. Native attestation (Play Integrity / App Attest) is not specified; web geolocation is spoofable by design. For venueless/at-home/live-event instances with null `places.lat`, `within_geofence` defaults false → no-show stays 0.5-weight unverified, which is the *intended* floor but also means proof-of-attendance is simply unavailable for a whole class of dates (acknowledged, but it means D3's protection is venue-only).

**A3 (MAJOR) — Retaliatory rating before reveal still leaks via timing + report side-channel.** D2 hides the *content* until both submit, but `submit_rating` with `p_unsafe=true` **immediately opens a `reports` row** (and SOS/disputed paths). A retaliator submits an `unsafe` rating first; the counterparty, though they can't read the rating, gets reported and may see standing/lock effects before they ever rate — the asymmetry the blind window was meant to remove. Also the rater learns the counterparty hasn't submitted (their own row stays unrevealed), a submission-status oracle.

**A4 (MINOR) — Missed-check-in escalation cannot distinguish "phone dead / had a great time" from "in danger."** D6 escalates silence to emergency-contact notification after 30m. False-positive rate will be high (dates run long, phones die), training contacts/users to ignore alerts — the cry-wolf failure mode for the *one* feature that's literally life-safety. No "snooze / I'm fine, stop asking" path is specified beyond the binary ok/alarm, and no rate-limit on contact spam.

**A5 (MINOR) — Self-report SOS opens a report with `target_id = p_user` (the reporter is the target).** `respond_safety_checkin('alarm')` writes `reports(reporter_id=p_user, target_id=p_user, reason='safety_sos')`. The *subject* of the SOS is the user-in-danger, not the perpetrator; T&S has no link to the counterparty/lock except via payload of an enqueued job. The report points the victim at themselves; the dangerous counterparty isn't named in the report row.

**A6 (MINOR) — Block is unilateral and irreversible (M8) → harassment-by-block / lock-griefing.** `block_user` cancels an active lock with `cancel_reason='safety'`, which trips §7.6 freeze and (per P5) may penalize the *other* party's instance. A bad actor can lock a date then block the counterparty seconds before, weaponizing the safety-cancel to freeze the victim's night with no recourse and no rate limit on blocks.

## 7. State / Lifecycle / Notification Gaps

- **L-1** — `safety_checkins` row creation is owned by P2 ("on `safety_checkin` job fire, insert a row") but B4 means that job never fires; so in practice **no safety check-in is ever created**, `respond_safety_checkin` has nothing to act on, and the escalation sweep finds an empty table. The entire D6 flow is inert end-to-end until B4 is fixed *and* P2 implements the creator.
- **L-2** — No notification is defined for: rating-window-closing-soon (so users submit before reveal), standing downgrade (`warned`/`cooldown` — D4 says "notification only" for warned but no notif is enqueued), dispute opened/resolved, or block confirmation. The plan claims notifications for check-in/reconfirm/escalation but only the alarm/escalation jobs are enqueued (and those are broken via B4).
- **L-3** — `rating_window_close` reveal has no handler (M5); lone ratings never auto-reveal.
- **L-4** — Impossible state: a lock can be `completed` and rated by both, then later `block_user` tries to cancel it — `block_user`'s `update locks ... where status='active'` no-ops on a completed lock (fine) but the chat-freeze and offer-revoke still run; partial propagation with no transaction-level assertion that *something* happened (idempotent but silent).
- **L-5** — No empty/loading/error contract for `safety_center` when the user has never locked a date (returns `[]` arrays — OK) or when `profiles_private` row is absent (`emergency_contact_on_file` returns NULL not false — three-valued; client must coalesce).

## 8. Mobile / Platform Concerns

- **MB-1** — Geofence check-in *requires* native location permission (spec §10 explicitly: location pre-filter + check-in "want native"). Web geolocation is both spoofable (A2) and frequently denied/coarse; `MAX_ACCURACY_M=200` will reject most desktop/web fixes, so on web the proof-of-attendance is effectively unavailable → all web no-shows fall to 0.5-weight unverified. The plan treats geofence as platform-agnostic; it is not.
- **MB-2** — The safety check-in push ("Are you OK?") and escalation are "load-bearing, not optional" per spec §10 and need native APNs/FCM; web push is "too weak." P7 leans entirely on P2's push, which itself defers native certs to a later phase. So at launch the *one* life-safety notification rides the weakest channel. Should be called out as a launch-blocking dependency, not a documented hand-off.
- **MB-3** — No offline/no-signal handling for check-in submission (venues with poor reception); a queued check-in submitted after the `[starts_at-30m, +duration+30m]` window is silently rejected by the DB time-guard → false "no proof" → A1 asymmetry hits the honest user.

## 9. Testing / Verification Gaps

- **T-1** — All SQL tests are unrunnable (B5) — the TDD "expect FAIL for the right reason, then PASS" loop is invalid; tests fail at fixture setup, not at the assertion under test, so a passing implementation could still "fail" and a broken one could "pass" once fixtures are patched.
- **T-2** — No test exercises the P8-migrated `reports` enum against P7's `'actioned'`/`'reviewing'` reads/writes (B2/B3) — the parity tests pin reliability math but **nothing pins the cross-phase enum contract**, which is where the real breakage is.
- **T-3** — No test asserts `can_enter_lock_flow` is actually *called* (it can't be — B1); the ladder's enforcement has no integration test, only unit tests of the pure evaluator. Green unit tests + dead enforcement = false confidence (exactly the "fake safety UI" failure mode the roadmap says P7 closes).
- **T-4** — Geofence test uses haversine but the DB time-window guard (`now() between v_start and v_end`) is untested with `time_range` (the test inserts `starts_at, duration_min` but `adjudicate`/`record` read `lower(di.time_range)` — generated column; need a test proving the window math with a real `time_range`).
- **T-5** — No abuse/security test: no test that a non-party cannot `submit_rating` as another user (R-1), no test that `safety_center` rejects other users (R-3). Security properties are asserted nowhere.
- **T-6** — Parity test pins only one input (3 perfect dates → 87.50). The recency-EWMA and unverified-weight branches in the TS oracle have vitest cases but **no SQL parity counterpart** — the SQL `power(0.5, (n-1-idx)/H)` could diverge from TS `Math.pow(0.5,(n-1-i)/H)` (numeric vs float rounding) and the single fixed point wouldn't catch it.

### Bottom line
The P7 internals (reliability EWMA, blind-until-both, geofence math, the pure evaluators with TS↔SQL parity) are genuinely good and well-tested in isolation. But the plan is graded on whether *executing it* yields a working, abuse-resistant safety system wired to the product — and on that axis it does not. The enforcement ladder enforces nothing (B1), the safety-report and dispute loops silently die against P8's schema (B2, B3, B6), the timers never fire against P2's schema (B4), every SQL test is unrunnable against the real schema (B5), and the headline geofence "proof" protects the wrong party (A1). These are not polish items; they are the difference between "safety system" and "safety theater." Fix B1–B6 and the §4 seams (especially S-2/S-3/S-5) and re-audit before any execution.
