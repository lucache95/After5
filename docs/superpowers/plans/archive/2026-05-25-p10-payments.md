## DECISION GATE — Binding payment vs. social convention

**The gap.** Spec §4 lists `pay_setting` as `I pay` / `they pay` / `50-50` and *already says* it is "an expectation, not a binding transaction; renegotiable/cancellable post-lock without penalty." But the product surfaces it like a feature, and the audit flags it (Critical #5): nothing makes it *true* — no hold, no escrow, no charge, no proof, no recourse. That is the **payments integrity gap** and the **pay-setting abuse/expectation problem** this slice closes.

### Option (a) — Make it binding (Stripe holds / escrow) — FUTURE, NOT BUILT
Put real money behind the setting: on lock, place an authorization hold / escrow for the paying party; capture or release at completion; refund on benign cancel; arbitrate on dispute.

- **Pros:** the promise is real; reduces bad-faith behavior; enables a future premium/marketplace business.
- **Cons (why not for launch):** money-transmission/marketplace regulation, KYC on payees, Stripe Connect onboarding, tax reporting, chargeback handling, refund/dispute SLAs; new high-risk financial PII (avoided in S1); marketplace cold-start tax on the very first dates; it **contradicts spec §4** ("renegotiable/cancellable without penalty" fights auto-capture escrow); and cost/build dwarf the launch need ("stop implying a guarantee we can't keep").

### Option (b) — Relabel as a non-binding social convention  ✅ RECOMMENDED & IMPLEMENTED
Treat `pay_setting` as **a heads-up about the vibe**, never a transaction:
1. **Canonical copy** (label + non-binding disclaimer) renders **everywhere** the setting appears. Source-of-truth strings live in one shared module so web + native + every surface stay consistent — and so the P4 label contradiction (CC5) is fixed at the source.
2. The disclosure appears at publish (create) **and** at view (feed/offer/lock/post-date), so neither side can claim a promised payment.
3. The canonical **`reports`** intake's `payment_dispute` category captures abuse and routes it to moderation (S9/P8) via the canonical `file_report` writer — without the platform touching money.

- **Pros:** cheap, ships now, removes the integrity gap immediately, no regulatory exposure, no new financial PII, faithful to spec §4, gives T&S a tracked-dispute lever.
- **Cons (accepted):** does not *enforce* payment. Payment is a social matter between consenting adults at a public venue; the platform's job is honesty + a paper trail.

**Decision: implement Option (b).** Option (a) is recorded below as a future design with no tasks.

```ts
// packages/business/src/pay-setting.ts
//
// Pay setting = a NON-BINDING social convention (Option b, S11 decision gate).
// A heads-up about the vibe, NOT a transaction. After5 moves no money for dates and
// makes no payment guarantee. These strings are the SINGLE source of truth for every
// surface (web today, native later) so the framing never drifts — and they resolve the
// P4 viewer-POV vs spec creator-POV label contradiction (CC5) by exposing both sets here.

// Mirrors the canonical `payment_preference` enum (owned by S1).
export type PaySetting = 'i_pay' | 'they_pay' | 'split';
export type PaySettingPerspective = 'creator' | 'viewer';

// Spec §4 creator-POV labels (shown to the night's author / on creation).
export const PAY_SETTING_LABELS_CREATOR: Record<PaySetting, string> = {
  i_pay: 'I pay',
  they_pay: 'They pay',
  split: '50-50',
};

// Viewer-POV labels (shown to a browser/responder; i_pay/they_pay invert because the
// viewer is the counterparty). This is the canonical wording the S5 feed card MUST use,
// replacing P4's locally-inlined strings (CC5).
export const PAY_SETTING_LABELS_VIEWER: Record<PaySetting, string> = {
  i_pay: 'They treat',
  they_pay: 'Your treat',
  split: '50-50',
};

export const PAY_SETTING_DISCLAIMER =
  "Just a heads-up about the vibe - not a guarantee. After5 doesn't process any payment; sort the bill out together in person.";

export interface PaySettingDisclosure {
  label: string;
  disclaimer: string;
  /** Always false in Option (b). Explicit so a future binding tier is a deliberate change. */
  isBinding: false;
}

export function describePaySetting(
  setting: PaySetting | null | undefined,
  perspective: PaySettingPerspective,
): PaySettingDisclosure | null {
  if (!setting) return null;
  const labels = perspective === 'creator' ? PAY_SETTING_LABELS_CREATOR : PAY_SETTING_LABELS_VIEWER;
  return { label: labels[setting], disclaimer: PAY_SETTING_DISCLAIMER, isBinding: false };
}

export function paySettingDisclosure(setting: PaySetting | null | undefined): string | null {
  return setting ? PAY_SETTING_DISCLAIMER : null;
}
```

```ts
import { z } from 'zod';

// Mirrors the CANONICAL DB enum `report_reason_category` (owned by S1; INTEGRATION-CONTRACT
// C5/C11.6). Keep in lock-step with that enum — do NOT add categories the DB enum lacks.

  'no_show_dispute',

  'fake_profile',
  'other',
]);

// Mirrors the canonical payment_preference enum (S1).

// A payment dispute (Option b: track, don't transact). Must reference the night or the

export const PaymentDisputeReportSchema = z.object({
  target_type: z.enum(['date_instance', 'lock']),
  target_id: z.string().uuid(),
  detail: z.string().min(1).max(2000),
  reason_category: z.literal('payment_dispute').default('payment_dispute'),
});
export type PaymentDisputeReport = z.infer<typeof PaymentDisputeReportSchema>;
```
