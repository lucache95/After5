# Launch branding audit — planner-era vs Barbiecore dating brand

Date: 2026-05-29
Scope: READ-ONLY. Catalog every surface a tester sees that is still planner-era / off-brand vs `docs/superpowers/DESIGN-SYSTEM.md` (Barbiecore dating language). Nothing changed.

## Target brand (reference)
Warm cream shell `bg-shell-base` #FAF4EC · hot-pink accent `shell-accent` #E0218A · deep-plum ink `shell-ink` #3D0F2E · Caprasimo (`font-heading`, lowercase) + Fredoka (`font-body`) · polaroid framing (`tone="dating"`) · spring motion · lowercase, dry, anti-earnest copy · no Kelowna hardcoding.

On-brand reference screens (already built, 5b): `app/feed/`, `app/matches/`, `app/offers/`, `app/nights/`, `app/onboarding/`, `app/home/`, `components/BottomTabShell.tsx`, NotificationBell/center. These use `shell-*` tokens + `font-heading`/`font-body` + lowercase dating copy.

The off-brand planner uses a different token set: `font-display` (Fraunces serif), `text-text`/`text-secondary`/`text-muted`/`text-accent` (warm-cream amber/rose), `bg-background`/`bg-surface`, "Plan my date" copy, Kelowna-hardcoded.

## Strategic question for the user
**Is the date-planner still a public entry point, or is dating the front door now?** This decides scope:
- If dating is the front door: `/` rebrands to the dating pitch, `/login` callback defaults to `/home`, planner pages (`/dates`, `/dates/[slug]`, `/plan`, `/account`) get hidden from primary IA or kept only as SEO/legacy (still styled planner-brand, that's acceptable if un-linked from the dating flow). The `/account`-vs-`/home` dual-dashboard split must be resolved.
- If both verticals stay public: landing needs to route to both, and the two brands (warm-cream planner vs Barbiecore dating) coexist by design — but the tester still hits planner copy first, which reads as off-brand for a dating launch.

A second, smaller decision: the `/home` teaser gallery and planner `itineraries` data are reused as dating "nights" filler — keep as placeholder content or replace with real posted nights.

## Notes on token migration cost
The foundation is already additive-done: Caprasimo (`font-heading`), Fredoka (`font-body`), and `shell-*` tokens exist alongside the planner's Fraunces/`text-*`/`bg-background`. Rebranding a planner surface = swap font + color token classes + rewrite copy, not a structural rewrite. Landing is the exception (full rebuild — its structure is the planner funnel).
